# InfoMapper – Decisions

Condensed record of the decisions taken while designing the prototype (UX, `D-xx`) and the application
(architecture, `AD-xx`). Status as of 2 October 2026. The working documents with full discussion live in Claude;
**this file is the copy the code follows**. When a decision changes, update this file in the same pull request.

Behaviour reference: `docs/prototype/infomapper-prototype-with-sources.html`. Data reference: `docs/data-model-v2.md`.

---

## UX decisions (D-xx)

### Canvas and mappings
- **D-01** The core of the canvas is mapping a source column to an attribute; layers (mappings, relationships) are toggled on one canvas.
- **D-02** A mapping is a model object, independent of any canvas. Removing a card does not remove its mappings.
- **D-03** The canvas is unbounded; the minimap is called “Overview”. The Overview's miniature also draws the visible notes in their paper colour, under the cards.
- **D-36** Attribute order belongs to the model (same on every canvas). Ctrl/Alt + ↑/↓ moves an attribute, Shift to top/bottom; drag in the entity panel. Source columns keep their physical order.
- **D-37** Card width (200–600 px) belongs to the canvas. Long names are truncated in the middle, keeping the part after the last underscore (`customer_addr…_line2`).
- **D-46** New entities: Entity tool (E) and toolbox on the canvas; “+” per concept in the left panel; “New concept”. The concept comes from the concept frame clicked into, else a picker with nothing preselected (D-72). Duplicate names warn, do not block. (Changed by D-72.)
- **D-48** Dragging a column onto an attribute without mappings creates a direct mapping. If the attribute already has a mapping, a choice appears: “Separate mapping (alternative source)” or “Add to mapping …”, pre-selected by a hint (same table: add; other system: separate). Enter confirms, Esc cancels. (Changed by D-76.)
- **D-49** A combined mapping: input lines meet in an ƒ node next to the attribute, one line continues; its status colours all its lines. The mapping panel has an Inputs section (order, add, remove); more than one input requires a rule, into which columns are inserted by click. Actions “Split into separate mappings” and “Merge mappings”. The attribute panel shows one row per mapping.
- **D-50** A combined mapping may use columns from different source systems; in Data Vault 2.0 mode the hints warn that it mixes systems (suggest a business rule in a later layer).
- **D-51** Changing an approved mapping's inputs, kind or rule sends it back to review and clears the approval; approval belongs to a version of the mapping. Changing only the note keeps the status. An import sends an approved mapping back to review, with a stored reason, when an input gets a type conflict it did not have, an input with the Business key classification (code BK, D-57) changes type, or a renamed input is named in its rule (the rule is rewritten). The reason is cleared by any change of the mapping's status or content. With four-eyes on, the person who ran the import counts as the mapping's last editor. Moving a mapping's input to another column after its column left the source, and deleting a column that is one input of a combined mapping, send an approved mapping back to review with the reason ("moved from {column} after it left the source", "{column} was deleted from the model"). A change to resolve about a mapping is settled by setting the mapping's status in its panel. (Extended in slices 7a, 7b and 7c.)
- **D-52** A row's right-click menu shows only that row's actions; card actions are only in the card header's menu, so deleting an attribute can't be mistaken for deleting its entity.
- **D-47** Deleting an entity from the model first shows its impact (attributes, mappings incl. approved ones, relationships, canvases, projects, requirements). A concept with entities is deleted only after its entities are moved to another concept; no cascade. Concept frames become free frames.

### Canvases, frames, selection
- **D-04** Frames belong to a canvas, not the model. One model, many canvases.
- **D-05** Dragging an entity into another concept’s frame asks explicitly; membership by drop position; one level of frames.
- **D-06** Drawing or resizing a frame does not take cards from other frames.
- **D-07** A collapsed frame becomes a block; its lines merge into one line per target with a count; layout is unchanged.
- **D-12** Canvas look (background, grid) is per canvas and outside undo.
- **D-14** A frame moves by dragging its name or any empty spot inside it.
- **D-15** Dragging empty canvas draws a lasso. Pan with scroll, Space, middle button; Shift+drag inside a frame draws a lasso.
- **D-16** The lasso selects only elements fully inside it.
- **D-17** A lassoed frame stands for its cards in the selection.
- **D-18** Right-drag pans; the Hand tool (H) pans with the left button.
- **D-19** Right-click without moving opens the toolbox for what is under the pointer (Ctrl+click on Mac, menu key). Right-clicking an unselected item selects it first.
- **D-22** Layer mode is per canvas; notation (crow’s foot / UML) is shared; Focus is momentary and not saved. A canvas also keeps two switches beside its layer: relationship lines between entities and between source tables, which filter within Everything and Relationships. (Extended by D-71.)
- **D-23** No nested frames for now.

### Working layer (labels, notes, context)
- **D-08** Working labels (e.g. `CR-23`) are stored apart from model tags (BK, PII).
- **D-09** Labels are assigned by hand first; automatic labeling is an option.
- **D-10** A live label canvas shows only labeled elements, with context cards for partly labeled ones. A label has at most one live canvas. Opening it makes a canvas named after the label in the current project, its elements arranged into frames by concept and system; elements that become labeled later land to the right of the content (no “Newly labeled” frame yet). Deleting the label turns its live canvas into a normal canvas in the same undo step; Duplicate layout of a live canvas gives a normal canvas.
- **D-11** Adding or removing a card on a live canvas changes the label, always after confirmation. Adding a card there labels its element in the same undo step (the Entity tool without a question); removing one takes the label off the element, or off the rows and mappings that bring it there when it is a context card. Bulk adds and removing several cards are not offered. Owners, admins and modelers do this; reviewers and readers see a live canvas read-only.
- **D-20** Notes belong to the canvas and the working layer. Free notes join the frame they are dropped in; pinned notes follow their card or frame with a dashed tether. Duplicate layout copies no notes. A note joins a frame only when dropped in it (drawing, resizing or fitting a frame never moves or claims notes). A note whose card or frame leaves the canvas stays as a free note at its place, in no frame.
- **D-21** Notes are open or resolved; resolved ones can be hidden, a preference kept per person in their browser only (not on the server, not an undo step); an empty new note disappears. Every note change is one undo step; anyone who may write notes edits any note, and its panel names who wrote it.
- **D-24** Labels extend to mappings, tables and columns; the active context comes after that, as an option. Merging mappings keeps the labels of the merged ones on the mapping that stays.
- **D-25** Live canvases include tables (fully labeled ones whole, others as context) and fade unlabeled mappings. Context cards have a dashed outline, a light header and “context only”, and show their relevant rows (the Labeled filter); relevant rows are bold; mappings without the label are faded by colour, never opacity.
- **D-26** An active working context labels every model change (entities, attributes, mappings; relationships through their entities), not layout changes, in the same undo step. It stays on after reload until switched off. The context is a per-person, per-workspace preference in the browser, sent with every write; the server checks it (the label exists, the person may change labels) and records it on every change event of the group. Only owners, admins and modelers have the switch. Moving an attribute labels only the moved attribute. Deletions are not labeled; source tables, columns and concepts are not labeled by the context. A change the context would label is refused when its label is gone, and the browser switches the context off; undo and redo never label. An import labels nothing, the mappings it sends back to review included. (Extended in slice 7a.)
- **D-53** A count of notes (a card's header, a collapsed frame's block) shows the notes you would see: open ones, and resolved ones while they are shown. Notes take part in the selection: a lassoed frame stands for its free notes, Ctrl+A takes the free notes outside frames, and a pinned note moves with its card or frame, never twice.

### Projects and navigation
- **D-27** One shared model per workspace; projects organise canvases and context. Isolation between clients comes from workspaces.
- **D-28** A canvas can belong to several projects. Removing a shared canvas only takes it out of the current project; deleting a project deletes only canvases no other project uses. A project is deleted from its home (slice 12a, D-65); the last project cannot be deleted. The order of a project's canvases is the project's own: moving a canvas in one project leaves its place in another. (Extended by D-71.)
- **D-29** Opening a project shows its home screen: canvas tiles with thumbnails, stats, labels (pinnable), open notes, requirements. Pinning a label to a project and unpinning it are one undo step each (slice 12a). Roles without label rights see a pinned label's plain ★, not the pin control. A canvas tile's thumbnail is a sketch of the canvas's layout: frames (a collapsed frame as its block, its cards, their lines and its free notes not drawn), entity cards in their concept's colour and table cards in the physical colour at the heights the canvas gives them, one line per table and entity pair joined by a mapping, free notes in their paper colour and requirement cards in the reserved violet; no text and no marks, and the layer mode is ignored. An empty canvas says "Empty canvas". The tile counts the canvas's cards and frames ("{n} cards, {m} frames"). A project's tile on the workspace home shows its project's first canvas's thumbnail. The home computes each drawing from the rows it reads on every load; the tile refers to it at an address keyed by its content and draws it through an external `<use>`, so its colours are the page's tokens in light and dark mode (AD-32; slice 12b).
  The thumbnails' part accepted by Łukasz, 1 November 2026 (the day slice 12b was merged).
- **D-35** Left panel groups fold (count, sticky headers, remembered, search opens matches); “Only on this canvas”. Inspector sections fold (remembered per title); page actions always visible; lists over 20 items get a filter and “Show all”.
- **D-38** Back and forward walk one navigation history, the browser's own: the two buttons before the breadcrumbs, Alt+←/→ outside text fields, the browser's back and the mouse's back and forward buttons; the breadcrumbs stay clickable. A place is a workspace home, a project home, a canvas, or one item selected on a canvas (a card, a row, a mapping, a relationship, a frame, a note, a requirement, a label, or an entity, attribute, table or column whose card is not on the canvas); panning and zooming, the workspace home's tab, a deselection, several items, a bundle, view state and the side panels are not. A selection is a history entry of its own without an address: its place is kept for the browser tab under the entry, not in the URL, and a reload starts without a selection. Going back to a selection selects it as a click would and never opens a hidden details panel (D-54); cards, rows, frames, notes and requirement cards are centred at the same zoom when they are off screen, while mappings, relationships and labels are selected without moving the view; one on another canvas opens that canvas at its remembered view first. A field being edited is saved before Back or Forward leaves it. A place that no longer exists shows what still does, with a toast: the canvas without a selection; for a canvas no longer in its project, the project's first canvas; for a project that no longer exists, the workspace home. (Changed in slice 6b.)
- **D-39** A view-state bar at the right end of a canvas page's breadcrumbs row shows everything that hides or fades items on the canvas (Focus, layer, hidden relationship kinds, filters, collapsed cards, collapsed frames, hidden resolved notes, active tool), each removable with its ×, plus “Show all” from two chips the person can remove. A live canvas's “Live: {name}” chip comes first, without ×, and its Labeled filter is not counted as filtered and is kept by “Show all”. The row's height never changes: chips that do not fit fold into “+{n}”, after the breadcrumbs above the current page have shrunk; its menu lists them with their ×, while “Live: {name}” and “Show all” stay visible. Removing the filters, the collapsed cards or the collapsed frames is one undo step, and so is what “Show all” changes of them; Focus, the layer, the hidden relationship kinds, hidden resolved notes and the tool are view state outside undo. People who cannot edit the canvas see the filter and collapsed-card chips without ×. The Changes view has a chip of its own. The Changes view and Focus exclude each other: turning one on turns the other off, and the chip says which one is on; "Show all" turns the Changes view off. (Changed in slice 6a: no lens since slice 4b-1, D-32; no role chip, the user indicator shows the role. Extended in slice 7b.) (Extended by D-71.)
- **D-54** Side panels: the object browser and the details panel are shown and hidden by the toolbar's buttons at its two ends, and resized by dragging their inner edge (left 200–520 px, default 264; right 280–640 px, default 340): while dragging only a guide line moves, and the panel and the canvas change size once, on release; double-click or Home resets, ←/→ change the width by 16 px, Shift by 64 px. Hidden panels and widths are remembered per person in the browser, on every page with the panels. A hidden panel stays in the page, inert. Selecting never opens a hidden details panel; actions that lead to details on purpose do (links that name what to show, menu items that edit a field in the panel, creating an element whose name is typed there, a requirement clicked in the left panel), and it stays open. Hiding, showing or resizing the left panel keeps the model where it is on the screen. A canvas's remembered view is stored with the canvas's left edge on the screen (the left panel's width; 0 when it is hidden or the window is up to 1000 px wide) and corrected by the difference when the canvas opens, in the same step that sets the view, so the model stands where it stood; views saved before slice 6a open unchanged. (Added in slice 6a.) Up to 1000 px wide both panels are hidden; a button slides one over the canvas (one at a time, not remembered), a selection does not open the details panel, and clicking an entity or a table in the left panel closes it. The view is stored at once after the canvas's own view changes, and every store takes the view and the left edge at the same moment; a view already stored is not stored again, and a changed view is stored before the page is left. (Extended by D-71.)

### Requirements and content
- **D-30** One requirements layer with kinds: business need, data requirement, business rule, data-quality rule, non-functional. Requirements can be broken down (parent).
- **D-31** Coverage is computed from a requirement's items. A linked entity is one item, a linked attribute is one, and a linked mapping makes its attribute one. Links to tables and columns are in scope but are not items, and nothing is pulled in implicitly: an entity link does not bring its attributes. An attribute item is covered when it has an approved mapping without a type conflict. An approved mapping from a column missing from source covers no requirement (slice 7a). A retired column has left the source, so its mappings cover no requirement either (slice 7b). An entity item is covered when at least one of its attributes is covered that way. A requirement is covered when it has at least one item and all of them are covered. Coverage reads “{m} of {n} covered”, its tooltip naming the parts (“1 entity, 3 attributes”). (Changed in slice 4b-1.) (Extended by D-70: a fact's or a dimension's attribute is covered by the same rule through its dimensional mappings.) (Changed by D-73: a calculated attribute is covered when every input is.)
- **D-32** On the canvas: requirement markers on entity and table cards (a violet diamond and the number of requirements the card's panel lists, the list as its tooltip). Selecting a requirement colours its scope without fading anything: attribute items' rows blue when covered and orange when a gap, entity items' headers the same way, linked columns' rows and linked tables' headers blue, and linked mappings' lines drawn lit. Below 40 % a card's summary (orange when any of its items in scope is a gap) stands for its rows, as a dot at the header's right end. In a collapsed frame's block, the member's row carries the same dot. Fading the rest is always Focus (D-22), also for a requirement. (Changed in slice 4b-1.) Requirement cards (D-41) draw a dashed line with an end dot to each element their requirement is linked to on the canvas: an entity's or table's card at its header, an attribute's or column's row, a mapping's middle; into a collapsed frame, the member's row in its block. The lines show in “Everything” and are hidden in “Mappings” and “Relationships”; they dim with the other lines on a selection, never on a hover. A requirement dragged from the left panel onto a row, a card or a mapping line is linked to it at once, with Undo; onto empty canvas it places its card. Under Focus a requirement card stays lit when its requirement is the target or its scope contains the focused element itself, and a trace line when both its ends are lit. (Changed in slice 4b-2.) (Extended by D-70: the logical attributes that feed the scope are coloured by their own coverage; Focus on a requirement lights its own dimensional mappings.)
- **D-33** Labels and requirements are separate; a requirement has an external reference; a label can be promoted to a requirement (later).
- **D-34** Element panels list each requirement once: direct ones first, with × to unlink, then indirect ones, without ×. An entity's come via its attributes (“via attribute”) or via mappings onto them (“via mapping”); an attribute's via mappings onto it (“via mapping”); a table's via its columns (“via column”) or via mappings that read them (“via mapping”). Mappings and columns show their own only. There is no “via entity”. Clicking a requirement opens its panel. (Changed in slice 4b-1.) Each row's “Place card” places the requirement's card next to the element (below its frame when the element is in one: a placed card never lies over a frame), or shows its card when it is on the canvas; a row dragged onto the canvas places the card where it is dropped; “Add all to this canvas” or “Add the {n} missing to this canvas” under the list. An entity or table panel whose card is not on the open canvas offers “Add to this canvas”. (Changed in slice 4b-2.)
- **D-41** Requirement card: 230 px, filled header in a reserved violet (excluded from the concept palette) with the kind's icon, the key and the kind's name; the name; a three-part coverage bar over the requirement's items (D-31): covered, mapped but not approved, not mapped (an entity item is mapped when any of its attributes has a mapping); the status badge and “{m} of {n} covered”. Below 40 % the header and a plain block. Selecting the card is selecting the requirement. A requirement has at most one card per canvas; its cards are layout, never frame members, carry no label on a live canvas and hold no pinned notes; Duplicate layout copies them. (Changed in slice 4b-2.)
- **D-42** Long texts (requirement descriptions, entity and attribute definitions, notes) use a rich-text editor dialog; panels show them formatted and shortened. Transformation rules and rule expressions stay code fields.
- **D-43** Text colour only from a named palette (warning, attention, confirmed, information).
- **D-44** New requirements get a template per kind: section headings are content, grey hints vanish when typing and are never saved, empty sections are removed on save.
- **D-45** Templates are built in now and editable per workspace later.

### Sources
- **D-55** Source import (slice 7a). A system is described once from a file in InfoMapper's source standard, a catalog query's result or DDL scripts, and re-imported the same way; the review shows everything an import would do before anything is written, and the import is one undo step. The source owns a column's name, position, type, nullable, keys and comment, and a re-import updates them; the comment is the source's and read-only (the modeller writes a note, D-57), and the review shows every overwrite. The modeller owns the classifications and the note: a re-import never changes them. The import reads every classification a file names, by code or current name; an unknown value, or a table classification named on a column, is warned about once per value and table and ignored; a new column is written with what matched; when the file differs from a column's classifications the review says so and keeps the modeller's. For new columns the file does not classify, the review suggests Business key (the only primary key column of a table with no business key, in the file or stored) and, in Data Vault 2.0 mode, Link key (a foreign key that is not a primary key); an unticked suggestion is not written, and the suggestions are part of what the review showed. A field the file leaves out is never compared or overwritten. Missing is a status, not a delete: a table, column or relationship not in the file gets “missing from source” and keeps its mappings, cards and links, and loses it when it comes back. Missing is judged only inside the scope the modeller picks: the imported schemas, or only the columns of the tables in the file; more than half of a system's columns going missing is warned about. Renames are the modeller's choice; the engine suggests one for the same position and type, and a rename keeps the column's identity. The server builds the plan again from the same text and choices and writes only when it does what the review showed; otherwise the review refreshes and says so. The working context labels nothing an import writes. A type the importer cannot read, and a table whose name differs only in case from another, are never passed over silently: the first is kept with a warning, the second left out of the import with its reason. The app has no sample files; for now one import takes up to 30,000 column rows (a limit of the local adapter, see known-limitations.md). An import raises the changes to resolve it finds and settles those the source settles (D-56); a table or column that comes back is no longer retired. (Extended in slices 7b and 7c.)
- **D-56** Changes to resolve (slice 7b). Every source change that needs a decision becomes a change to resolve, stored as it was found (kind, severity, the object, a label that survives a rename or a delete, a detail) and settled with a resolution, who and when; resolved changes stay as the system's history. The kinds: a column or a table left the source; a new column or table in a system imported before; and, for a mapping the import sent back from approved, a type conflict, a business key column that changed type or a rule rewritten for a renamed column. A business key column that changed type with no such mapping is a change of its own. A business key column is one with the Business key classification (code BK); such a change settles when its column loses the classification or the classification is removed (D-57). High when an approved mapping is affected or a business key changes type; normal otherwise. The review shows the changes and the requirements whose coverage changes before the import; afterwards they wait on the system's and table's panels, counted in the tree and the status bar. Every action shows what it does first and is one undo step: retire keeps a table or column as historical (a mapping is historical only when every input is retired; a retired input shows "until" the day it left); delete removes it from the model with its mappings, relationships and cards after showing them and the coverage change (D-47); move points the inputs that read the column at another; map to an attribute (a draft); not needed, which "Mark as needed" takes back; decide a new table column by column; approve the mapping again, only when it fits the source and following four-eyes; leave it in review; acknowledge a business key change. "Approve again all" approves the mappings one import sent back that fit and that the person may approve, and lists the others apart with the reason. A change settles itself when the source settles it (back in the source, gone before a decision) or when its object is deleted or its question answered elsewhere, each time with a resolution that says so; nothing is dropped silently. Reviewers approve again, leave in review and approve all; the other actions are for owners, admins and modelers. The changes slice 7a's imports left were derived when slice 7b was installed. The project home's model consistency and the canvas's Changes view show what source changes touch; the Changes view only fades, it changes no data or layout. (Extended in slice 7c.)
- **D-57** Classifications and notes (slice 7c). A workspace keeps one list of classifications for its source tables and columns: 19 built in from its creation (general ones and Data Vault 2.0 ones; Effective date is general; the code PII is named "Personal data") and its own. Every one can be renamed and removed and own ones added; a removed built-in one can be restored, empty, while its name is free. Built-in classifications keep a fixed code (BK, PII, LK…) that the app's rules read, so a renamed one keeps working and a removed one is absent; the rules' own texts name the role, not the classification. Names are unique per scope against every name and built-in code, compared ignoring case, spaces, `_`, `-` and `/`; a new name is also the name an import file must use. Removing one shows first where it is used and, for a built-in one a rule reads, what stops, and takes its links with it; each change is one undo step. A business key change without a mapping settles when its column loses Business key or Business key is removed. Owners, admins and modelers edit the list and set classifications from the table and column panels; reviewers, readers and an archived workspace see them read-only. With Data Vault 2.0 mode off, Data Vault classifications stay stored and are hidden in the panels and the reading; switching the mode off says how many uses stay stored. Classifications are links (AD-15, AD-18), read through one index per load; on the canvas only source rows' BK badge and the Keys filter read them (the PII badge belongs to attributes). Tables and columns have the modeller's note, plain text like a mapping's note, apart from the source's comment, which is read-only. When slice 7c was installed, the columns' business key and personal data flags became classifications and the column comments no import had written moved into the columns' notes, listed in a report. Classifications on attributes and the entity panel's Data Vault hints are not part of it. (Changed by D-78.)
- **D-78** Metadata conventions (slice 23). A workspace's conventions have one place, the workspace home's tab "Metadata conventions", between People and Settings, which every member sees: its classification list (D-57's dialog moved there; "Edit the list…" in a table's or a column's panel opens the tab), its concepts' colours (moved from Settings; D-76's rules unchanged) and its naming conventions. Settings keeps a box "Model conventions" with one sentence and a button that opens the tab. Every classification has an optional definition, plain text. An own classification may get a code when it is added, never changed afterwards: letters, digits and `_`, starting with a letter, at most 30, upper-cased; unique in the import's comparison (case, spaces, `_`, `-` and `/` ignored) against every code of the workspace, built-in ones and those of removed and deleted classifications included, so a code is never given twice, also after its classification's add is undone; and codes and names of the same scope never collide in that comparison, in either direction. The import matches an own classification by its name or its code. Built-in classifications are told by their origin, never by having a code, and only they can be restored. A workspace gets its built-in classifications' names and definitions in its documentation language when it is created (English, Polish, German), chosen in a "Documentation language" select wherever a workspace is created: beside the top bar's "New workspace" and with an organization's first workspace; English by default. Changing the language later renames nothing and rewrites no definition; when slice 23 was installed, the built-in classifications of existing workspaces kept their names and got the definitions in their workspace's language. Removing a classification that is used or that a rule reads shows D-57's form first, in a small dialog; any other is removed at once, with Undo. Names, definitions, codes, removals, restores and colours are each one undo step, for owners, admins and modelers in a workspace that is not archived; reviewers, readers and an archived workspace see the tab read only. The naming conventions are plain text, a workspace setting outside undo, edited by owners, admins and modelers with the workspace's version (D-59); nothing checks names against them yet. The map from physical to logical types, an organization's default conventions and a reset to a language's defaults are later (entity stereotypes came in slice 24, D-79). Accepted by Łukasz on 10 November 2026.
- **D-79** Entity stereotypes (slice 24). A workspace keeps a list of entity stereotypes in the Metadata conventions tab, in a box "Entity stereotypes" between Classifications and Concept colours: the five built in (`object`, `link`, `dictionary`, `context`, `informative`), which can be renamed and defined but never removed (`object` is every new entity's stereotype and every fact's and dimension's, C-5), and the workspace's own, after them in the order they were added. Each has a name, an optional plain-text definition and a code. An own stereotype's code is required, proposed from its name while the code field is not edited by hand (lower case, diacritics removed, every run of other characters one `_`, no `_` at either end, `s_` before a leading digit, at most 30), letters, digits and `_`, starting with a letter; it is set when the stereotype is added and never changed. Names and codes are compared as D-78 compares them (case, spaces, `_`, `-` and `/` ignored), in either direction: a name is refused when another live stereotype has it or when it is any stereotype's code, removed and deleted ones included (its own code does not count); a code is refused when any stereotype has it, removed and deleted ones included, so a code is never given twice, also after its add is undone. A refused name or code is shown under its field. An entity keeps its stereotype's code, never its name, so a rename or a definition changes no entity, import or export: the card's first line (with the definition as its title), the Model tab and the entity panel's select (each option's definition as its title, the chosen one's under it) show the workspace's name. The domain checks on every write that every live entity's code is a live stereotype of its workspace; the SQL schema has a composite foreign key on `(workspace_id, code)`, the local adapter none (its keys point to ids; known limitation). Undo refuses a revert that leaves an entity on a stereotype no longer in the list, or that brings back a stereotype whose name another one has or is another's code. Removing an own stereotype that entities have opens a dialog that asks which stereotype they get instead and moves them in the same undo step; an unused one is removed at once, with Undo. A new workspace gets the built-in names and definitions in its documentation language; when slice 24 was installed, existing workspaces got the English names and the definitions in their language, and an entity's code outside the five in an older file became an own stereotype named by its code, with one log line. Renaming, defining, adding and removing are each one undo step, for owners, admins and modelers in a workspace that is not archived; reviewers, readers and an archived workspace see the box read only. Facts and dimensions keep `object` and show their InfoCube role. Reordering the list, hiding an unused built-in one, another default stereotype, naming rules per stereotype and a colour or an icon per stereotype are later. Accepted by Łukasz on 10 November 2026.
- **D-58** Organizations and sign-in (slice 8). InfoMapper starts from nothing: on the start page a person creates an organization, with themselves as its owner and a workspace with an empty first project and canvas and the 19 built-in classifications, or signs in. ### Model checks

- **D-75** Model checks (slice 20). The model is checked as it stands, read only: nothing is stored, dismissed or changed by a check. ## Architecture decisions (AD-xx)

### Organizations, workspaces, access
- **AD-01** A user can belong to several organizations. A workspace belongs to one organization; people from outside are invited to a workspace as guests. Note (slice 8): Until guests from other organizations are built (later, `docs/ideas.md`), a guest is a workspace member without a row in the workspace's organization; slice 8 adds no new guests, and adding a guest to another workspace of the same organization keeps them a guest (D-58).
- **AD-02** Workspaces share nothing live; patterns are copied. An organization library comes later.
- **AD-03** Model versions are named baselines (frozen snapshots) to compare with and to generate documents from. No model branches.
- **AD-04** Sign-in with e-mail and password (Supabase Auth) to start; Microsoft/Google/SSO later. Note (slice 8): Until the database slice, sign-in in development is an organization's shared password, scrypt on the server, with a signed session cookie that carries the organizations unlocked in it (D-58); Supabase Auth with a password per person replaces it.
- **AD-05** Five roles per workspace: owner, admin, modeler, reviewer (read, comment, notes, approve), reader. Reviewers write, resolve, move, pin and delete any note as modelers do; working labels are changed by owners, admins and modelers only; readers read notes and labels. Reviewers change a requirement's status only. Note (slice 8): Owners and admins add people, change roles and remove people; only an owner gives, takes or changes the Owner role, and nobody changes or removes their own row (slice 8, D-58). Note (slice 9): Owners, admins and modelers edit a project's name and description (`project.edit`), as they create projects and rename canvases; reviewers and readers do not (D-59). Note (slice 12a): Owners, admins and modelers delete a project (`project.delete`, D-65). Note (slice 25): A member of any role may create, change and delete a module's own objects outside the model that only they see (InfoDocumenter's private documents): the core action `module.own_objects`, every role, never in an archived workspace; the module's own rules decide the rest (sharing and changing shared documents with `model.edit`).
- **AD-06** Four-eyes approval (the author cannot approve their own change) is a workspace setting, off by default. Every approval is logged. For requirements, setting Agreed is the approval; the author is whoever last changed its content (kind, name, description, expression, severity).
- **AD-07** After sign-in the user lands on the workspace home. The top bar shows Organization / Workspace / Project.
- **AD-08** Optional Data Vault 2.0 mode per workspace: hints only, nothing enforced. In the mode, the Data Vault classifications show in the panels, the import suggests Link key, and a source table panel shows its Data Vault reading (hub, links, link keys, dependent child, driving and multi-active keys, effective dating, satellites with personal data apart), read from the classifications and the source's keys; nothing is created. (Extended in slice 7c.)
- **AD-09** Workspace lifecycle: create (empty or copy), archive (read-only), transfer to another organization, delete (owner only, after export).

### Data (see `docs/data-model-v2.md`)
- **AD-10** Table groups as in the data model; every model and work table has `workspace_id`.
- **AD-11** UUID v7 ids generated by the application; human keys (`REQ-104`) per workspace.
- **AD-12** Every row has `version`, `created_at/by`, `updated_at/by`, `deleted_at` (soft delete).
- **AD-13** Append-only `change_event` log with before/after images and the active context label; one user action = one change group = one undo step. A change group's change events carry the active working context's label (`context_label_id`).
- **AD-14** Baselines are JSON snapshots of the model part of a workspace.
- **AD-15** Requirement and label links: one table per kind, one nullable FK per target type, “exactly one” check.
- **AD-16** Canvas layout as rows (`canvas_item`, `frame`, `note`); canvas look as JSON.
- **AD-17** Rich text stored as sanitized HTML plus a plain-text copy.
- **AD-18** Portable core: no enum types, triggers, stored functions or arrays; closed lists as text with CHECK; JSON only for look, snapshots and change images. Postgres/Supabase extras only outside the core. Note (slice 25, amended in slice 26): a fourth place for JSON: a document's recipe (`document_definition.scope`, `cover`, `style`, `sections`), read and written whole and never searched; the domain checks its shape with the style's and the section kinds' schemas, and a recipe stored in an older shape is read through the module's row upgrade.
- **AD-26** A mapping can read several source columns (`mapping` + `mapping_input`); a direct mapping has exactly one input.
- **AD-27** Attribute type = logical type plus optional length, precision, scale; `custom` has a name.
- **AD-28** Business key is also an attribute property, suggested from input columns with the Business key classification (code BK, D-57).

- **AD-24** Canvas engine: **React Flow, with named workarounds** (closed 3 October 2026 after the spike and its follow-up; report in `spikes/canvas-react-flow/REPORT.md`). ### Modules
- **AD-33** InfoCube is a module of the one application (slice 15a). Its code lives in `src/modules/infocube/`, in InfoMapper's five parts (domain, data, ui, canvas, app), each under its layer's rules; InfoMapper's layers never import a module, and `npm run lint` checks it (`tests/layer-rules.test.ts` lints probe files in each layer that import a module or the composition root and expects the lint to refuse them). `src/compose/` is the composition root: the only code that names the modules, imported only by `src/app`. A module enters InfoMapper only through named extension points, each plain data or a function the composition root hands over. Two bind every module: its tables are in the table registry (undo, the local adapter's rules and the data file's shape; the build fails when a module's table is missing from one of them, and a guard test checks every table the migrations create against them), and its rows that point to a deleted InfoMapper row are deleted in the same change group. The others are listed in `CLAUDE.md`, kept up to date in each sub-slice. A module's tables point to InfoMapper's, never the other way. With no module registered, InfoMapper behaves as before. Note (slice 25): two more extension points: **document sections** (a module registers section types: their options' schema, a pure builder of the content tree from the document's model state, their words in the documentation languages and their options as plain data for the form; the content tree's types and the section contract are InfoMapper's domain, `src/domain/document/`; InfoDocumenter stores and renders them without importing the module) and **the workspace home's module tab**. Two modules never import each other.
- **AD-34** An entity has a model level, `logical` or `dimensional`, set when it is created and never changed; a write that would change it is refused (slice 15a). Facts and dimensions are dimensional entities; their dimensional description (role, grain, SCD type, measures) lives only in InfoCube's tables, which point to InfoMapper's. The model level is the one InfoMapper column InfoCube needs. InfoMapper's rules read it: a relationship joins two entities of one level, an attribute is pasted within one level, the duplicate-name warning compares within one level, and a source column maps only to a logical attribute (dimensional attributes are fed from the logical model through dimensional mappings). InfoMapper's lists and counts are of the logical level (the Model tab, the homes' and the status bar's counts, model consistency, the import review, the attribute pickers); canvas tiles and tab counts count every card. InfoCube also reads relationship roles, which InfoMapper keeps for every relationship (D-68). Model checks (slice 20, D-75) cover both levels: duplicate names, calculations and lost originals at both, copied keys at the logical level, and the modules' groups through the composition root; model consistency stays logical only.
- **AD-35** Modules are licensed per organization and turned on per workspace by an owner or admin, off by default; turning one on needs the organization's licence (slice 15a). A module is on when its workspace's switch is; the licence is read only when it is turned on. A module is turned off only while the workspace has none of its objects, so turning it off deletes nothing; while it is off, nothing creates or brings back one of its objects (a create, copy, paste, undo or redo). The settings show the module's box to everyone; without the licence it says "{organization} has no InfoCube licence." and its check box is disabled. Granting and ending a licence are not commands yet: in development a script grants one. A workspace's copy stays in its organization and takes the module's switch and objects with it; a transfer, or a copy into another organization, of a workspace with a module on is refused unless that organization holds the module's licence ("{organization} has no InfoCube licence. Delete this workspace's facts and dimensions and turn InfoCube off, or transfer it to an organization with the licence."); a workspace with the module off moves freely. Note (slice 25): A module whose objects are outside the model (InfoDocumenter's documents) can be turned off while it has objects; they are kept and hidden, and come back when it is turned on again. InfoDocumenter's licence is the module `infodoc`; without it the box says "{organization} has no InfoDocumenter licence."
